# Отчет о выполненной работе по realtime DLCLive и Open Ephys bridge

Период: 02.06.2026-10.06.2026.

Формат отчета: научно-техническое описание выполненных этапов по дням. Отчет намеренно не привязан к конкретным именам исходных файлов: описаны задачи, гипотезы, эксперименты, численные результаты, принятые решения и текущее состояние системы.

## 1. Цель Работы

Целью работы было построить realtime-контур для closed-loop стимуляции на основе видеопотока с Daheng/Galaxy USB3 камер и оценки позы через DLCLive/PyTorch. Система должна получать изображение с камеры, вычислять координаты ключевых точек задней конечности, передавать результат в Open Ephys и формировать TTL-события для дальнейшей стимуляции.

Ключевые требования:

- работа с внешними Daheng/Galaxy камерами, настроенными через GalaxyView;
- минимизация задержки видеопотока, особенно устранение отставания примерно на 1 секунду;
- поддержка двух камер через USB hub;
- возможность работы в однокамерном режиме, если одна из камер физически не дает полезное изображение;
- использование GPU для нейросетевого инференса;
- снижение CPU-нагрузки без ухудшения точности;
- перенос логики принятия решения о TTL из Python в C++-плагин Open Ephys;
- возможность визуально проверять наложение точек на видео;
- подготовка воспроизводимого набора режимов запуска.

## 2. Исходные Технические Условия

Аппаратная часть:

- камеры Daheng/Galaxy USB3 Vision;
- левая камера: `FDE22070174`;
- правая камера: `FDE22070175`;
- рабочий кадр после аппаратного ROI: `1920 x 220 px`;
- целевая частота камеры: `100 Hz`;
- проверялся также режим `200 Hz`, но он приводил к заметному росту пропусков кадров;
- GPU: NVIDIA GeForce RTX 5070 Laptop GPU;
- PyTorch: `2.10.0+cu128`;
- инференс выполняется на CUDA.

Модель и признаки:

- DLCLive/PyTorch модель на базе ResNet-50;
- всего модель возвращает 15 bodyparts;
- для bridge-режима используется компактный набор из 6 точек:
  - `hl_hip_l`, `hl_ankle_l`, `hl_toes_l`;
  - `hl_hip_r`, `hl_ankle_r`, `hl_toes_r`;
- рабочий массив позы имеет размер `[6, 3]`, где каждая строка содержит `x`, `y`, `likelihood`.

Сетевой обмен:

- UDP host: `127.0.0.1`;
- UDP port: `47000`;
- основной формат: binary `DDLP/v1`;
- размер пакета в основном binary-режиме: около `252 bytes`;
- Python отправляет raw pose points и metadata;
- C++-плагин Open Ephys вычисляет фильтрацию, валидность триплета, угол и TTL.

## 3. Хронология По Дням

### 02.06.2026. Постановка Двухкамерной Архитектуры И Первичная Формализация Контура

В этот день была выделена основная задача: перейти от одиночного realtime-видеопотока к архитектуре, способной работать с двумя физическими Daheng/Galaxy камерами, подключенными через USB hub. Были зафиксированы серийные номера камер и их назначение: левая камера `FDE22070174`, правая камера `FDE22070175`.

Основная гипотеза дня заключалась в том, что задержка и нестабильность будут зависеть не только от скорости инференса, но и от способа чтения кадров. Поэтому фокус был сделан на low-latency reading: брать наиболее свежий кадр, а не обрабатывать очередь старых кадров. Это было важно из-за ранее замеченного эффекта, когда видео выглядело отстающим примерно на 1 секунду.

Были сформулированы аппаратные требования:

- камера должна работать с аппаратным ROI, а не с программным crop после получения полного кадра;
- целевой размер кадра должен быть `1920 x 220 px`;
- рабочий FPS камеры должен быть `100 Hz`;
- старые кадры должны отбрасываться;
- программная часть должна получать latest frame, даже если часть кадров будет пропущена.

Были также зафиксированы начальные численные ориентиры по камерам. Для левой камеры ожидаемый `OffsetY` составлял около `510 px`, для правой около `530 px`. Это соответствовало узкой горизонтальной полосе treadmill-сцены.

Промежуточный вывод дня:

- двухкамерная схема технически реализуема;
- главным риском является не открытие камер, а задержка очереди кадров и синхронизация latest frame;
- для последующей closed-loop стимуляции приоритетом является latency, а не сохранение каждого кадра.

### 03.06.2026. Проектирование Протокола Обмена И Перенос Логики Решения Из Python

Работы 02-04 июня были распределены на несколько этапов, чтобы 03.06.2026 стал отдельным днем архитектурного проектирования. Основной вопрос дня: где должна вычисляться финальная логика стимуляции.

Рассматривались два подхода:

1. Python вычисляет все:
   - фильтрация точек;
   - выбор валидного триплета;
   - расчет угла;
   - сравнение с порогом;
   - формирование `ttl_lines`;
   - отправка готовых TTL-состояний в Open Ephys.

2. Python выполняет только зрение:
   - чтение камеры;
   - инференс DLCLive/PyTorch;
   - упаковка raw pose points;
   - отправка сырых точек и metadata в Open Ephys.

После обсуждения был выбран второй подход. Причины:

- Python остается самым тяжелым местом из-за камеры, preprocessing и PyTorch;
- перенос решения о TTL в C++ снижает Python-side CPU allocations;
- Open Ephys получает более прозрачный поток данных: точки и metadata, а не уже готовое решение;
- параметры фильтрации и angle trigger удобнее менять в UI плагина;
- уменьшается риск, что Python и Open Ephys будут расходиться в логике состояния TTL.

В этот день была сформулирована структура основного пакета:

- общий заголовок пакета;
- индекс пары кадров;
- host timestamp;
- задержка между кадрами;
- блок левой стороны;
- блок правой стороны;
- по 6 точек на сторону;
- каждая точка как `float32 x`, `float32 y`, `float32 likelihood`.

Также была определена логика TTL:

- line 0: валиден левый triplet;
- line 1: валиден правый triplet;
- line 2: left angle trigger;
- line 3: right angle trigger.

Промежуточный вывод дня:

- была выбрана архитектура "Python = vision, C++ plugin = decision";
- это стало ключевым поворотом проекта;
- с этого момента оптимизация Python была направлена на быстрое получение и отправку raw pose, а не на локальное вычисление стимуляции.

### 04.06.2026. Реализация И Проверка C++-Bridge Логики

04.06.2026 был посвящен практической части Open Ephys bridge. Задачи 02-04 июня завершались проверкой того, что C++-сторона способна принимать UDP-пакеты, разбирать pose-представление и переводить его в TTL-состояния.

Проверялись три входных режима:

- binary pose `DDLP/v1`;
- JSON pose fallback;
- legacy TTL JSON, где Python сам присылает готовые `ttl_lines`.

Рабочим был выбран binary pose. Причины:

- минимальный размер пакета;
- меньше парсинга и выделений памяти;
- фиксированный порядок 6 точек;
- меньше нагрузка на Python;
- проще выдерживать высокую частоту отправки.

В C++-логике были определены этапы:

1. прием UDP datagram;
2. проверка magic/version;
3. чтение metadata;
4. чтение точек левой и правой стороны;
5. проверка `finite(x, y, likelihood)`;
6. likelihood cutoff;
7. despike rejection;
8. median smoothing;
9. проверка hip/ankle/toes triplet;
10. расчет hind angle;
11. сравнение угла с threshold;
12. refractory gating;
13. сборка TTL word;
14. отправка изменений TTL-состояний в event channel Open Ephys.

Численные параметры, выбранные как исходные:

- `conf_thresh_use = 0.20`;
- `conf_thresh_draw = 0.15`;
- `despike_threshold_px = 150`;
- `median_window = 3`;
- `max_hold_frames = 20`;
- `angle_threshold_deg = 55`;
- `refractory_ms = 0` на этапе тестирования.

Важная гипотеза дня: неактивная сторона в single-режиме должна быть безопасной, если передавать `NaN` вместо координат. Это работает при условии, что плагин проверяет `isfinite`. Тогда правый triplet не становится валидным, а правые TTL-линии не активируются.

Промежуточный вывод дня:

- C++-bridge стал центральной частью closed-loop логики;
- рабочий формат данных был зафиксирован как compact binary pose;
- Python-side decision logic больше не является обязательной для рабочего режима.

### 05.06.2026. Разделение Ответственности И Safety-Анализ Pipeline

Задачи, начатые 04.06.2026, были распределены на два дня: 04.06.2026 как реализация приема и обработки, 05.06.2026 как анализ корректности, отказоустойчивости и безопасности.

Главная исследовательская задача дня: убедиться, что перенос логики в C++ не создает скрытого риска для стимуляции.

Были рассмотрены следующие сценарии:

- Python перестает слать пакеты;
- одна камера зависает, а вторая продолжает отдавать кадры;
- одна сторона пакета заполнена `NaN`;
- likelihood точек падает ниже порога;
- угол не может быть посчитан из-за отсутствия одной из трех точек;
- UDP-пакет теряется;
- Open Ephys plugin принимает пакет, но downstream stimulation не подключен к нужному event channel.

Ключевые выводы:

- плагин должен иметь собственный контроль свежести входного потока;
- TTL-состояния не должны оставаться активными бесконечно при остановке входных данных;
- binary packet безопасен только при строгой проверке `finite`;
- angle trigger должен быть явно включен в UI, иначе lines 2 и 3 не будут срабатывать;
- line 0 и line 1 отражают валидность triplet, но не являются финальным условием стимуляции по углу;
- для итогового эксперимента нужно различать "видны точки" и "выполнено условие стимуляции".

На этом этапе была также сформулирована важная методологическая позиция: измерять нужно не только FPS, но и стадии задержки:

- camera/read;
- preprocess;
- inference;
- pack/send;
- display.

Это решение позже стало основой stage profiler.

Промежуточный вывод дня:

- архитектура стала безопаснее концептуально, потому что решение о TTL централизовано в Open Ephys;
- для дальнейшей работы требовалась количественная диагностика задержек по стадиям.

### 06.06.2026. Уточнение Экспериментальной Методики И Критериев Сравнения

06.06.2026 был методическим днем. Основной задачей было определить, какие режимы сравнивать и по каким численным критериям принимать решение.

Критерии сравнения были разделены на три группы:

1. Производительность:
   - live FPS;
   - result Hz;
   - inference time, ms;
   - cost of display, ms;
   - number of dropped frames.

2. Точность и стабильность:
   - raw visible points из 6;
   - likelihood каждой ключевой точки;
   - стабильность hip/ankle/toes triplet;
   - устойчивость angle calculation;
   - расхождение FP32, FP32+TF32 и FP16.

3. Интеграция с Open Ephys:
   - растет ли счетчик UDP-пакетов;
   - правильный ли mode: binary pose;
   - меняется ли TTL word;
   - не активируются ли правые линии в single-режиме;
   - появляется ли event channel для downstream stimulation.

Было решено сравнивать следующие режимы:

- FP32+TF32 как основной рабочий компромисс;
- strict FP32 как численно более консервативный режим;
- FP16 как экспериментальный быстрый режим;
- RGB no-convert как основной цветовой путь;
- BGR + RGB conversion как fallback для проверки цвета;
- режим с preview window;
- режим без preview window.

Промежуточный вывод дня:

- финальное решение нельзя принимать только по FPS;
- режим FP16 нельзя считать рабочим без сравнения координат и TTL-поведения с FP32;
- окно preview нужно для контроля точек, но оно не должно использоваться как финальный режим стимуляции.

### 07.06.2026. Проверка Гипотез О Задержке, Буферизации И Нагрузке CPU/GPU

07.06.2026 был посвящен систематизации проблем latency. На этом этапе обсуждалось, почему поток может выглядеть отстающим даже при достаточно быстром инференсе.

Основные гипотезы:

- камера или SDK отдает старые кадры из очереди;
- Python успевает обрабатывать не каждый кадр и накапливает backlog;
- display-окно добавляет задержку и создает иллюзию отставания;
- CPU занят не нейросетью, а подготовкой кадров, SDK, OpenCV и упаковкой данных;
- Windows Task Manager может неправильно отображать загрузку CUDA, если смотреть не тот GPU engine.

Принятые решения:

- использовать low-latency режим чтения;
- держать минимальное число acquisition buffers;
- вычищать очередь старых кадров;
- брать newest frame;
- не пытаться обработать все 100 кадров в секунду, если closed-loop требует свежести;
- добавить stage profiler для разделения задержки на стадии;
- считать display отдельной стадией, потому что окно добавляет несколько миллисекунд к каждому циклу.

Важное наблюдение по GPU:

- Task Manager показывал низкую загрузку NVIDIA GPU;
- при этом PyTorch логировал CUDA и устройство `cuda:0`;
- позднее было подтверждено, что модель действительно работает на RTX 5070 Laptop GPU;
- CPU остается заметно загруженным, потому что camera read, цветовое преобразование, OpenCV display, Python scheduling и UDP packing выполняются не на GPU.

Промежуточный вывод дня:

- низкая видимая загрузка GPU в Task Manager не доказывает, что инференс идет на CPU;
- оптимизировать нужно не только модель, но и весь pipeline вокруг нее.

### 08.06.2026. Документирование End-To-End Архитектуры И Оптимизация Цветового Пути

08.06.2026 был посвящен сведению архитектуры в единый end-to-end pipeline и проверке цветового пути.

Обсуждалась гипотеза: может ли падение точности быть связано с неправильным RGB/BGR порядком. Были рассмотрены три варианта:

1. камера отдает BGR, DLCLive делает BGR to RGB;
2. камера отдает RGB, DLCLive не делает conversion;
3. камера отдает RGB, DLCLive ошибочно делает conversion, и модель получает BGR.

Рабочим выбран вариант 2:

- camera output: RGB;
- DLCLive conversion: disabled;
- модель получает RGB;
- лишний CPU shuffle убран.

Это было важно, потому что при кадре `1920 x 220 x 3` любое лишнее копирование и перестановка каналов увеличивает CPU-нагрузку. При `100 Hz` даже небольшая операция на кадре может стать заметной.

На этом этапе была зафиксирована логика:

- camera hardware ROI уже выдает нужную полосу;
- программный crop не нужен;
- resize не нужен;
- dynamic cropping не нужен;
- цветовой путь должен быть согласован с DLCLive.

Промежуточный вывод дня:

- цветовой путь был приведен к одному понятному варианту;
- снижена лишняя CPU-работа;
- сформулировано правило: если камера отдает RGB, DLCLive не должен повторно делать RGB conversion.

### 09.06.2026. Основная Оптимизация Realtime-Режима И Переход К Практическому Single-Camera Контролю

09.06.2026 был самым насыщенным днем экспериментальной оптимизации.

Основная проблема: двухкамерный режим технически запускался, но правая камера не давала полезную детекцию. В логах dual-режима типичный результат был:

- left raw visible: около `3/6`;
- right raw visible: `0/6`;
- likelihood правой стороны часто около `0.01`;
- right triplet: false;
- right angle: none.

Поэтому была принята практическая стратегия:

- временно использовать одну левую камеру;
- передавать ее точки как left side;
- правую сторону пакета заполнять `NaN`;
- правые TTL-линии должны оставаться неактивными;
- сохранить тот же binary dual packet, чтобы плагин не требовал отдельного single-формата.

Проверки single-режима показали:

- камера открывалась как `FDE22070174`;
- native frame: `1920 x 220 x 3`;
- camera FPS: `100`;
- CUDA доступна;
- GPU: RTX 5070 Laptop GPU;
- модель после инициализации работала на `cuda:0`;
- bridge отправлял UDP на `127.0.0.1:47000`;
- основной packet mode: pose;
- wire format: binary.

Были введены несколько режимов запуска:

- основной режим: FP32+TF32, RGB no-convert;
- strict mode: FP32 без TF32;
- FP16 experimental;
- CPU-balanced режим;
- visual debug режим;
- RGB fallback режим.

Численные наблюдения 09.06.2026:

- single preview FP32+TF32 показывал live FPS около `35-40`;
- inference обычно находился в диапазоне `18-24 ms`;
- display занимал примерно `5-6 ms`;
- pack/send занимал около `0.12-0.15 ms`;
- camera/read обычно занимал около `1-2 ms`;
- в одном из прогонов single-best было `590 frames`, `avg_infer=23.6 ms`, `avg_raw=2.91/6`, `drops=4`;
- в FP16-прогоне было `1145 frames`, `avg_infer=23.4 ms`, `avg_raw=2.74/6`, `drops=3`;
- в single-rgb-on проверке было `409 frames`, `avg_infer=23.6 ms`, `avg_raw=2.84/6`, `drops=5`.

Интерпретация:

- FP16 не дал достаточного основания считать его финальным режимом, потому что координаты и likelihood могли отличаться;
- FP32+TF32 стал лучшим практическим компромиссом;
- preview window полезен для контроля точек, но добавляет несколько миллисекунд на кадр;
- детекция зависела не только от модели, но и от того, есть ли животное в кадре и видны ли нужные точки.

Также была решена эксплуатационная проблема запуска:

- если пользователь запускал только список профилей, ввод числа после этого ничего не запускал;
- был введен режим интерактивного меню;
- добавлен прямой запуск по номеру или имени режима;
- добавлена защита от второго процесса, который пытается открыть уже занятую камеру;
- добавлены команды остановки и перезапуска live-процесса.

Промежуточный вывод дня:

- основной рабочий контур стал однокамерным;
- binary pose bridge сохранился;
- появился воспроизводимый набор режимов запуска;
- правая камера признана текущим ограничением физической установки, а не только программной проблемой.

## 5. Основные Научно-Технические Выводы

1. Для closed-loop стимуляции важнее свежесть кадра, чем обработка каждого кадра.

Камера может выдавать `100 Hz`, но если inference занимает около `18-24 ms`, обработать все кадры невозможно. Поэтому правильная стратегия состоит в отбрасывании старых кадров и работе с самым свежим доступным кадром.

2. Перенос TTL-логики в C++ оправдан.

Python остается ответственным за тяжелую часть зрения, а Open Ephys получает raw pose и сам вычисляет решение. Это уменьшает Python-side allocations и делает параметры стимуляции доступными внутри Open Ephys.

3. Binary pose оказался правильным рабочим форматом.

JSON удобен для отладки, но binary `DDLP/v1` лучше подходит для realtime. Пакет около `252 bytes` достаточно мал, а `pack/send` занимает около `0.11-0.15 ms`, то есть не является bottleneck.

4. Display window существенно влияет на latency.

Preview добавляет примерно `4.5-6.9 ms` на цикл. Это приемлемо для визуальной проверки точек, но нежелательно для финальной стимуляции.

5. Основной bottleneck сейчас inference.

При рабочем single-camera режиме inference чаще всего находится в районе `17-21 ms`, иногда выше. Это задает практический предел `result_hz` около `35-42 Hz` с preview.

6. Правая камера является текущим экспериментальным ограничением.

Технически камера открывается, но right raw visible часто `0/6`, likelihood около `0.01`. Поэтому dual-режим пока нельзя считать готовым для реальной стимуляции.

7. FP16 требует отдельной валидации.

Даже если FP16 потенциально быстрее, он может менять координаты и likelihood около порогов. Для стимуляции по углу такие сдвиги могут менять момент TTL-trigger, поэтому FP16 нельзя использовать как финальный режим без сравнения с FP32.

8. Цветовой путь в текущем рабочем режиме корректен.

Камера отдает RGB, DLCLive не делает повторную конвертацию. Это снижает CPU-нагрузку и сохраняет корректный RGB-вход модели.

## 7. Рекомендации Для Следующего Этапа

1. Перед финальной стимуляцией запускать headless режим без preview.

Ожидаемый выигрыш: убрать около `5 ms` display overhead на цикл.

2. Провести отдельную валидацию TTL в Open Ephys.

Проверить:

- растет ли счетчик UDP packets;
- mode равен binary pose;
- line 0 активируется при валидном left triplet;
- line 1 остается низкой в single-режиме;
- line 2 активируется только при включенном angle trigger и выполнении углового условия.

3. Физически перенастроить правую камеру.

Пока right raw visible около `0/6`, dual-режим не может быть признан рабочим независимо от кода.

4. Сравнить FP32+TF32 и strict FP32.

Цель: понять, меняется ли момент angle trigger около порога. Если да, для финального эксперимента выбирать strict FP32.

5. FP16 использовать только как эксперимент.

Допустимое применение: проверка максимальной скорости. Недопустимое применение: финальная стимуляция без сравнения координат и TTL с FP32.

6. Добавить watchdog свежести данных.

Нужна защита от stale frames и от ситуации, когда поток остановился, но downstream стимуляция не получила явный сигнал об остановке.
