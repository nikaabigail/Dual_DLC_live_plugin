# Полный разбор кода DLC realtime, сверенный с логами (2026-06-15)

Система: real-time трекинг задней лапы крысы одной камерой Daheng → поза по UDP в плагин Open Ephys → плагин по углу лапы даёт TTL-стимуляцию (замкнутый контур). Разбор построен на чтении кода + сопоставлении с реальными логами (`single_rt_dlc_live_bridge_debug.log` за 06-09/06-10/06-15, бенчмарки, легаси `rt_dlc_*`).

| **Gen2 — DLCLive standalone** | `rt_dlc_live.py` (его `main()`) | `config_rt_dlc_live.py` | `rt_dlc_live_debug.log` (2026-06-01) | reference; **но файл `rt_dlc_live.py` активен как библиотека** |

## 1. Сквозной путь одного кадра (боевой single-best)

Цикл `single_rt_dlc_live_bridge.py:234-339` — **синхронный, однопоточный, без очередей**: один кадр → один инференс → один UDP-пакет.

```
камера.read()  →  run_raw_inference()  →  raw_pose_result (6 точек)  →
make_pair_result (реальная сторона + пустышка-NaN)  →  bridge.send() [252-байтный UDP]  →  следующий read()
```

Период итерации ≈ `camera/read (~1.1мс) + inference (~16мс) + pack/send (~0.1мс)` ≈ 17 мс → потолок **~58 Гц**. Система **упирается в инференс**, камера на 100 Гц свободно бежит, лишние кадры намеренно выбрасываются (см. §3).

## 2. Конфиги и профили: что реально применяется

Настройки живут в 3 слоях, накладываются друг на друга через `setattr`:

```
config_rt_dlc_live (база)
  └← config_dual_rt_dlc_live  (делает `from config_rt_dlc_live import *` + добавляет DUAL_*)   ← ЭТОТ модуль использует bridge
       └← словарь профиля single-best (apply_profile = setattr на модуль)
            └← CLI-флаги (--no-display и т.п.)
```

`run_live_profile.py` — тонкий лаунчер: выбирает профиль, по `target` решает какой скрипт звать (`single`→bridge), проверяет через WMI не занята ли камера другим процессом, и запускает дочерний python. Сам он модель/камеру не трогает.

**Эффективный single-best:** `PRECISION=FP32`, `CROPPING=None`, `RESIZE=1.0` (камера уже отдаёт полосу 1920×220 аппаратно), `GALAXY_OUTPUT_COLOR=rgb` + `CONVERT_TO_RGB=False` (кадр уже RGB, лишний BGR↔RGB не нужен), `DUAL_TORCH_ALLOW_TF32=True`, `DUAL_TORCH_CUDNN_BENCHMARK=True`, `DUAL_TORCH_COMPILE_BACKEND=cudagraphs` (новое), `NUM_THREADS=12`, UDP `127.0.0.1:47000` `mode=pose wire=binary`.

> ⚠️ Баннер «LIVE PROFILE…» печатается только в **stdout**, в `.log` его НЕТ. Профиль постфактум из лога восстанавливается лишь косвенно (по строкам `TORCH_BACKEND`, `Single bridge started … precision=FP32`).

## 3. Захват с камеры + Galaxy SDK + критический fallback

Весь вход — класс `GalaxyCameraSource` (`rt_dlc_live.py:112-491`), инстанцируется из `dual.build_camera_runtime`. `_prepare_sdk_environment` чинит PATH/DLL под gxipy.

**Сердце фотометрической проблемы — `_import_or_apply_config` (rt_dlc_live.py:278-292):**
1. Сначала пробует `cam.import_config_file(...)` — заливает в камеру **весь** .txt-конфиг, включая `Gain`, `BalanceWhiteAuto`, `Gamma`.
2. Если вызов падает (в т.ч. USB3-ошибка) и `fallback_apply_config=True` → пишет warning «Applying core camera settings manually» и зовёт `_apply_core_config_file`.
3. **Ручной fallback применяет только `_read_core_config_values` (строки 329-352): геометрия, частота, `ExposureTime`, триггер. В наборе НЕТ `Gain`, `GainAuto`, `BalanceWhiteAuto`, `Gamma`.** → при сбое импорта усиление и баланс белого остаются заводскими/прежними, экспозиция же из файла подхватывается. Это и есть рецепт «картинка не из обучающего распределения».

**Цветовой тракт настроен верно** (`_raw_image_to_bgr`): BayerRG8 → SDK дебайеризует в RGB, `GALAXY_OUTPUT_COLOR=rgb` → массив идёт как RGB без лишнего перекодирования, `convert2rgb=False`. То есть **BGR/RGB — НЕ причина**; причина — яркость/усиление/WB.

**NEWEST_ONLY + drain** (`_drain_to_latest`): камера 100 Гц свободно бежит; чтобы не копить задержку, перед инференсом выбрасываются все накопленные кадры кроме свежего (до `MAX_DRAIN_FRAMES=20`). Поэтому **`drops` в логах — это намеренно выброшенные хостом кадры, а НЕ потери камеры**. Когда инференс быстрый — `drops=0`; при срыве (frame=5280 06-15: инференс 193 мс) drain мгновенно бьёт в кап 20 и далее ползёт вверх.

> ⚠️ **Важная оговорка по доказательствам:** строки `0x800F`/`import_config_file failed` **нет ни в одном `.log`** — warning пишется в логгер `rt_dlc_live`, у которого в bridge нет файлового хендлера. Сбой импорта на 06-15 виден в **консоли** (которую вставлял пользователь), а не в файле. Более того, строка `native={…ExposureTime:4000…}` парсится из **.txt-файла** (`parse_galaxy_config`, 9 ключей), а **не читается обратно из железа** — это «что записано в файле», а не «что реально в камере».

## 4. Инференс: DLCLive + PyTorch + cudagraphs

Самый дорогой этап (~90% бюджета кадра). Путь: `dual.run_raw_inference` → `DLCLive.process_frame` (при `CROPPING=None/RESIZE=1.0/convert2rgb=False` почти no-op, отсюда `preprocess=0.00`) → `runner.get_pose` (под `@torch.inference_mode`).

- **FP32**: `.half()` включается только при `PRECISION=="FP16"`; у нас FP32 — математика в float32 (сознательно, ради стабильности триггера).
- **TF32 + cudnn.benchmark** (`configure_runtime_backends`) — это НЕ FP16: тип остаётся float32, но матмулы/свёртки идут на тензор-ядрах с укороченной мантиссой (быстрее). Подтверждено логом `TORCH_BACKEND … cudnn_benchmark=True allow_tf32=True`.
- **cudagraphs** (`maybe_compile_runner_model`, новое): ровно один раз после init `runner.model` оборачивается в `torch.compile(backend="cudagraphs")`; eager-копия сохраняется; при любой ошибке компиляции **или** компилированного инференса — авто-откат на eager. cudagraphs переигрывает **те же** ядра → позы **бит-в-бит** → для триггера нейтрально. (В отличие от `inductor`, который перегенерил бы ядра и требовал бы accuracy-gate.)

**Эффект по логам:** до — 06-09 eager inference ~21 мс / ~42 Гц; после — 06-15 `TORCH_COMPILE applied backend=cudagraphs`, раннее окно inference ~15.6 мс / ~58 Гц. Низкая/нестабильная точность на 06-15 — **не дефект инференса** (cudagraphs бит-в-бит), а испорченный вход (см. §6).

## 5. Поза → триплет → угол → TTL: где это и почему «спит»

**В боевом single-пути Python НЕ считает ни триплет, ни угол, ни TTL.** При `DUAL_FAST_POSE_ONLY=True` он только инференсит, берёт 6 точек задней лапы и шлёт их сырыми. Вся «умная» часть (выбор стороны, фильтр, угол, порог, TTL) — в **плагине Open Ephys** (вне этого репозитория).

- **6 «мостовых» точек** (`DUAL_USE_POINTS`): `hl_ankle_l/r, hl_hip_l/r, hl_toes_l/r` (из 15 точек модели). Лог: `bridge points=[…]`.
- **Реальный порог видимости в бою — `CONF_THRESH_DRAW=0.15`, а НЕ `CONF_THRESH_USE=0.20`.** 0.20 живёт только в `OnlinePoseProcessor`, который в single-best **не подключён**. Проверено арифметикой: frame=2280 06-15 даёт `raw_visible=5/6` при `hip_r:0.17, toes_r:0.19` — эти точки проходят 0.15, но не 0.20. (Свой порог у плагина может быть третьим.)
- Полная цепочка `pick_triplet → normalize_triplet → angle_from_canonical → _angle_trigger` в коде **есть, но в single не вызывается** — это dual/референс. `pick_triplet` выбирает сторону **покадрово по максимуму уверенности, без гистерезиса** → даже когда всё работает, сторона может дребезжать.

**Почему низкая уверенность ломает контур:** триггеру нужны ОДНОВРЕМЕННО 3 точки одной стороны выше порога. Одна точка просела — триплета нет, угол не считается, TTL падает. На 06-15 постоянно `raw_visible=1..3/6`, иногда `0/6` → триплет мерцает, и хуже того — **мерцает сама сторона** (см. §6).

## 6. Точность детекции: разбор по сессиям (главное)

Реконструкция по строкам `frame=… raw_visible=N/6 p=hl_ankle_l:…` (печатаются каждые 120 кадров, `p=` — сырой confidence без сглаживания).

| Сессия | Exposure / Gain | Победившая сторона | Уверенность | Вердикт |
|---|---|---|---|---|
| **06-09** | 8000 / 10 (исходный) | LEFT 96% | hip_l=0.73, ankle_l=0.66, toes_l=0.54 | ✅ здоровая детекция |
| **06-10** | гуляет 8000→4000 | LEFT ~79% (при 4000 — 84%) | hip_l=0.62 | ✅ ещё нормально |
| **06-15** | 4000 / **24** (правленый) | **RIGHT 64%, LEFT 36%** | hip_l=0.27, hip_r=0.39 (обе слабые), toes≈0.21 | ❌ катастрофа |

**Контрольное сравнение (важно):** при **одинаковой** экспозиции 4000 06-10 здорова (LEFT 84%), а 06-15 сломана (LEFT 36%). Раз экспозиция та же, а результат противоположный — **дело не в экспозиции, а в gain/балансе белого/распределении**. В файле конфига прямо видно ручную правку: `Gain 24 #10` (подняли 10→24, причём 24 > AutoGainMax=22), `ExposureTime 4000 #4000`, `BalanceWhiteAuto Continuous`.

**Два слоя проблемы:**
1. **Фотометрика (обратимо):** правка gain/экспозиции + (вероятно) сбой импорта → Gain/WB не применились → яркость/цвет вне обучающего распределения → провал уверенности. Лечится возвратом к 8000/gain10 ИЛИ тем, чтобы `import_config_file` отработал и применил Gain+WB.
2. **Модельная неоднозначность лево/право (нужно дообучение):** на 06-15 сторона **осциллирует внутри одной сессии** (кадры 120-2040 правые, 2160-2400 внезапно левые; по сессии 26 кадров «правый голеностоп» против 17 «левый»). Левая и правая лапа геометрически почти зеркальны; как только картинка чуть уходит от обучающей, модель не может их различить. Это **не лечится экспозицией** — нужна доразметка/дообучение на более разнообразных данных.

> Производительность тут ни при чём: 06-15 даже быстрее (cudagraphs, ~15.8 мс/~57 Гц) — обвалилась именно **точность**.

## 7. Мост в Open Ephys: что реально на проводе

Пакет **DDLP/v1, 252 байта** на кадр (`_build_binary_pose_payload`): заголовок 36 Б (`magic DDLP`, version, pair_index=номер кадра, `host_time=time.time()`, …) + **два блока сторон по 108 Б** (left, потом right): шапка стороны (frame_id, source_frame_id, `capture_ts`, infer_ms, drops, raw_visible) + 6 точек × (x,y,likelihood) float32.

- Реальная камера заполняет свою сторону (`SINGLE_PLUGIN_SIDE`), вторая — **всегда NaN** (чтобы плагин держал её TTL-линии в нуле).
- Координаты идут **полностью сырыми** — без despike/медианы/выбора стороны. Если модель уверенно поставила точку не на ту сторону, мост это не отфильтрует — обе стороны уходят как есть.
- `send_every=1` → шлётся каждый кадр. Сокет неблокирующий (UDP не вешает realtime); потеря пакета молча уходит в warning, счётчика нет.
- Стоимость `pack/send` ~0.1 мс — <1% бюджета. **Угол/TTL в пакете НЕТ** — их считает плагин.

## 8. Производительность: как читать цифры

`StageProfiler` держит `last_ms` (мгновенное) и `avg_ms` (EMA, alpha=0.1 → реагирует за ~10 кадров, гасит выбросы). Две частоты в `stage_profile`:
- **`result_hz` = кадры/время за последнее окно** (~120 кадров) — текущая пропускная способность.
- **`total_hz` = кадры/время от старта** — накопительное, занижено холодным стартом; в начале всегда ниже result_hz и подтягивается. Низкий total_hz в начале — **артефакт усреднения, не дефект**.

**Честная оговорка по 06-15:** сессия делится на два режима. Раннее чистое окно (кадры ≤3000): inference ~15.9 мс, result_hz ~57. Позднее (>3000): inference ~21.6 мс, result_hz ~40, drops 0→13, два разовых стопора (185 и 135 мс avg — вероятно GC/USB/фон). То есть **«15.6мс/58Гц» — это лучшее раннее окно, а не устойчивое состояние всей сессии**; к концу просело почти к до-cudagraphs уровню. Но даже усреднённо cudagraphs дал выигрыш против 06-09 (~21мс/~42Гц).

**Почему ~58, а не 100 Гц камеры:** цикл синхронный однопоточный, inference-bound (период ≈17 мс). **Запас Гц под даунстрим-математику** берётся из того, что Python в боевом режиме почти ничего, кроме инференса, не делает (~1.5 мс не-инференсного коста из ~17 мс), а тяжёлый угол/TTL вынесен в плагин. Ускорив инференс (cudagraphs→TRT), освобождаешь Гц; держа инференс на узком ROI, а большой кадр — только под математику/отображение, получаешь и Гц, и большой кадр.

## 9. Сводка рисков для замкнутого контура

1. **Тихий fallback камеры**: при сбое импорта Gain/WB не применяются, кадры не помечаются как невалидные, контур продолжает считать угол по плохой позе. Нет гейта достоверности на уровне захвата.
2. **Дребезг стороны без гистерезиса**: `pick_triplet` выбирает сторону покадрово; на шумных confidence угол и TTL дребезжат. Та же логика в плагине.
3. **Порог триггера вне репозитория**: реальный `angle ≤ threshold` и порог уверенности — в плагине Open Ephys; из этого кода момент стимуляции не верифицируется.
4. **Наблюдаемость**: для боевого пути нет CSV (только debug-лог раз в 120 кадров); warning о сбое импорта не пишется в файл; `native={}` показывает файл, а не железо; одноразовая стоимость захвата cudagraphs-графа не логируется.
5. **Документационные расхождения**: нота профиля обещает «~21→17мс» (реально ~15.6); путаница `CONF_THRESH_USE 0.20` vs реально работающего `CONF_THRESH_DRAW 0.15`.
