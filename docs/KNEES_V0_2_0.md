# v0.2.0-rc2: два колена в существующем конвейере

Добавлены `hl_knee_l` и `hl_knee_r`. Это дополнительный режим Dual DLC Live, а не отдельная реализация обработки. Старые профили по умолчанию продолжают отправлять прежние шесть точек. Новый профиль `single-knees-strict` подключает модель с коленями и расширенный пакет.

## Исправление повторного обнаружения в rc2

В rc1 и базовой версии `filterPoint` после длительной потери точки допускал новое наблюдение в другом месте, но оставлял старые координаты в медианном буфере. Поэтому первые результаты повторного обнаружения могли оказаться далеко от текущего животного, даже если сама сеть предсказывала точку правильно. Это подтверждено на сохранённом видео: скачок обработанного колена на 651 px при изменении сырого предсказания примерно на 1 px.

В rc2 медианное окно ограничено возрастом кадров: вместе с координатами хранится `frame_id`. При принятии новой точки из окна удаляются наблюдения с возрастом `>= median_window`. При окне 3 учитываются только принятые точки из текущего и двух предыдущих кадров. После перезапуска счётчика либо разрешённого повторного обнаружения после `despike_reset_gap_frames` история очищается целиком. Это исправляет и длинные потери, и короткие пропуски, при которых раньше медиана смешивала далёкие по времени положения.

Исправление применяется к штатному фильтру всех точек, поскольку ошибочная история затрагивала также hip/ankle/toes. При непрерывных последовательных кадрах результаты совпадают с прежней медианой. При регулярном шаге frame_id=2 остаётся медиана двух доступных наблюдений; при шаге >=3 и окне 3 используется только текущая принятая точка. Это намеренное ограничение возраста данных, в том числе в двухкамерном режиме с пропуском кадров между инференсами. Размер окна выражен в кадрах источника, не в количестве успешных детекций.

Порог разрешённого повторного обнаружения в despike остаётся `despike_reset_gap_frames` (по умолчанию 15); меньшие пропуски сами по себе не разрешают принимать скачок больше 150 px. Hold, пороги уверенности, форматы пакетов и правила выбора стороны не переопределяются.

Это целевое исправление ошибки, а не полная идентичность координат rc1 после потери отслеживания. Рассчитанный по исправленным координатам угол и решение его validity gates могут отличаться именно на таких переходах. Интерполяция и анатомическое восстановление точек не добавлены. Изменение не устраняет все ошибки самой модели.

## Что проходит через плагин

1. Захват кадра и штатный `LegRoiTracker`, окно 448×220.
2. Штатный DLC-Live/PyTorch, новый профиль strict FP32. Для этой модели нулевая подкладка до кратности 32 применяется после crop/resize; исходная система координат сохраняется.
3. Штатные `raw_pose_result` и `make_pair_result`.
4. DDLP/v1: прежние шесть строк и две дополнительные строки коленей в конце. Новый приёмник принимает как 6, так и 8 точек. В JSON также поддержаны необязательные колени.
5. **Тот же C++ `filterPoint`** обрабатывает колени с отдельным состоянием для каждого имени и камеры: порог уверенности, отсечение выбросов, медиана, опциональное удержание и сброс после пропусков. Отдельного Python-фильтра для коленей нет.

Колени не добавлены в существующие триплеты выбора стороны и угла. Старый угол `hip–ankle–toes`, фазовая логика и назначение TTL сохраняются. Коленный угол `hip–knee–ankle` не подменяет прежнюю метрику.

ROI закреплён за прежними восемью именами `hl_toes/ankle/hip/iliac` для левой и правой стороны. Поэтому появление двух новых выходов не изменяет управление окном при одинаковых координатах прежних точек.

## Запуск нового профиля

Нужна собранная DLL этого дополнения: старый приёмник поддерживает только 6 точек и отклонит пакет из 8. Plugin API остаётся 10. Установка DLL выполняется по [BUILD_PLUGIN.md](BUILD_PLUGIN.md).

Готовая Release-сборка Windows x64 и экспорт модели доступны в [релизе v0.2.0-rc2](https://github.com/nikaabigail/Dual_DLC_live_plugin/releases/tag/v0.2.0-rc2). Файл модели — `DLC_r_tm_side_knees_full_v3_snapshot-best-050_dlclive.pt`; параметры обучения и ограничения описаны в [карточке модели](KNEE_MODEL_CARD.md). Веса скачиваются отдельно и не хранятся в Git-истории. Для этой версии используйте DLL из релиза либо `dist/windows-x64-release`, а не историческую Debug-сборку.

```powershell
$env:DLC_LIVE_KNEE_MODEL_PATH = 'C:\path\to\exported_17_point_model.pt'
C:\dlc_live_env\Scripts\python.exe .\python\single_rt_dlc_live_bridge.py --profile single-knees-strict --no-display
```

Путь к новой модели задаётся явно; рабочая старая модель не перезаписывается. Для новой модели профиль проверяет её declared constant-zero padding. В файле модели должны быть оба колена и прежние точки. Старые профили продолжают работать с прежним форматом; переключение профиля обратно восстанавливает исходный путь модели.

Встроенное окно Python (`--display`) остаётся отладочным просмотром сырых предсказаний, как в прежней версии. Оно не получает обработанные точки обратно из C++. Для проверенного видео после C++ используется описанный ниже офлайн-путь; это различие не следует скрывать.

## Видео с фактическим ROI и C++-постобработкой

Инференс ролика использует те же функции runtime. Камера заменяется чтением файла; пакет сериализуется в файл, без отправки на установку:

```powershell
C:\dlc_live_env\Scripts\python.exe .\scripts\preview_knees_roi.py infer `
  --video 'C:\path\to\rat.avi' `
  --model 'C:\path\to\exported_17_point_model.pt' `
  --output 'C:\path\to\preview'
```

Получаются `raw_roi_poses.npz` (все 17 сырых точек, окна и маршрут камеры), `native_packets.ddlp` и manifest с параметрами/хешами. Формат файла пакетов: повторяющиеся `uint32 LE length` и точные байты DDLP/v1. Запуск не использует отдельную геометрическую модель выбора стороны.

После сборки тестовой цели `DualDLCLiveBridge_tests` выполняется штатный C++-парсер и фильтры в офлайн-харнесе:

```powershell
$env:DDLC_REPLAY_INPUT = 'C:\path\to\preview\native_packets.ddlp'
$env:DDLC_REPLAY_OUTPUT = 'C:\path\to\preview\native_filtered.jsonl'
& 'C:\path\to\DualDLCLiveBridge_tests.exe' --gtest_filter=DualDLCLiveOfflineReplay.ReplayFile
```

`DDLC_REPLAY_CONFIG` при необходимости задаёт путь к JSON с именами штатных параметров и их значениями. Без файла используются значения по умолчанию из C++. Для повторения конкретной установки надо использовать её фактические настройки.

```powershell
C:\dlc_live_env\Scripts\python.exe .\scripts\preview_knees_roi.py render `
  --output 'C:\path\to\preview' `
  --native-jsonl 'C:\path\to\preview\native_filtered.jsonl'
```

`full_roi_native.mp4` показывает весь кадр и точное окно инференса. `review_roi_native.mp4` добавляет увеличение этого же окна. На видео рисуются прошедшие C++-фильтр hip/knee/ankle/toes только окончательно выбранной C++ стороной. Колено выделено кольцом. Рендер не сглаживает координаты повторно и не меняет сторону.

Команда `render` требует `ffmpeg` в `PATH`; сам инференс и C++ replay видеокодировщик не используют.

Сырые 17 точек хранятся отдельно от результатов фильтрации. Нельзя подменять вход плагина визуальной маской с заранее удалённой дальней стороной: штатные фильтры и окончательный выбор стороны должны получать исходные данные.

## Проверки совместимости

- `python/tests/test_knee_runtime.py`: старый пакет 252 байта и новый 300 байт, порядок строк, профиль/возврат к старой модели, неизменность ROI, padding после crop/resize и восстановление глобальных координат.
- `open_ephys_plugin/DualDLCLiveBridge/Tests/DualDLCLiveOfflineTests.cpp`: старый/новый пакет, опциональные колени в JSON, тот же point filter, пропуски/выбросы/медиана/hold/reset, возраст истории, некорректные пакеты и равенство результатов прежних шести точек при передаче 6 либо 8 точек в одном и том же runtime.
- Прежние Python- и C++-тесты остаются частью регрессии.

Проверки с фиксированными прежними координатами подтверждают совместимость добавленных полей и обработки. Они не означают, что новая обученная модель выдаёт те же координаты прежних точек. Офлайн-replay подтверждает обработку точек/выбор стороны/углы, но не проверяет аппаратную задержку TTL или работу на животном. Тестовый метод запрещает воспроизведение на экземпляре процессора с активным сокетом/потоком и не эмитит TTL.
