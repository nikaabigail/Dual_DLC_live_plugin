Отчет о выполненной работе: realtime DLCLive и Open Ephys bridge

Период: 02.06.2026-10.06.2026

Тема: разработка и проверка realtime-контура для closed-loop стимуляции на основе видеопотока с Daheng/Galaxy камер, оценки позы через DLCLive/PyTorch и формирования TTL-событий в Open Ephys.

1. Краткое резюме для всех читателей

За время работы был собран и проверен прототип системы, которая получает видеопоток с высокоскоростной камеры, определяет положение ключевых точек задней конечности животного и передает эти данные в Open Ephys для дальнейшей стимуляции. Главная идея текущей архитектуры: Python занимается зрением и нейросетевым инференсом, а плагин Open Ephys на C++ принимает сырые точки и сам решает, какие TTL-линии должны быть активированы.

Практически рабочим на данный момент является режим с одной левой камерой. Двухкамерная схема технически подготовлена, но правая камера в текущей физической установке не дает надежного изображения животного, поэтому ее пока нельзя использовать для финального closed-loop решения.

Текущее рабочее состояние: одна левая камера FDE22070174, кадр 1920 x 220 px, частота камеры 100 Hz, нейросеть на GPU RTX 5070, передача данных в Open Ephys по UDP 127.0.0.1:47000.

2. Что Было Сделано В Итоге

  • Настроен realtime-захват изображения с Daheng/Galaxy USB3 камеры с аппаратным ROI 1920 x 220 px.
  • Реализован low-latency подход: система берет свежий кадр и не накапливает очередь старых кадров.
  • Подготовлена двухкамерная схема для камер FDE22070174 и FDE22070175.
  • Выбран основной формат обмена с Open Ephys: compact binary пакет DDLP/v1 размером около 252 bytes.
  • Перенесена логика фильтрации, проверки триплета, расчета угла и TTL из Python в C++-плагин Open Ephys.
  • Создан рабочий single-camera режим, где левая камера передается как активная сторона, а правая сторона безопасно заполняется NaN.
  • Добавлены режимы запуска для FP32+TF32, strict FP32, FP16, CPU-balanced и RGB fallback.
  • Добавлен stage profiler, который показывает задержку по стадиям: camera/read, preprocess, inference, pack/send, display.
  • Подготовлен режим визуальной проверки точек и отдельный headless-режим без окна для финальной стимуляции.

5. Хронология Работы По Дням

02.06.2026 - постановка двухкамерной архитектуры

В этот день была сформулирована задача перехода от одиночного видеопотока к архитектуре с двумя физическими камерами. Были зафиксированы серийные номера камер: левая FDE22070174, правая FDE22070175. Главная гипотеза дня: задержка системы определяется не только скоростью нейросети, но и способом чтения кадров из камеры.

  • Целевой кадр: 1920 x 220 px.
  • Целевая частота камеры: 100 Hz.
  • Левый ROI: примерно OffsetY = 510 px.
  • Правый ROI: примерно OffsetY = 530 px.
  • Принято решение брать самый свежий кадр и отбрасывать старые.

Вывод: для closed-loop стимуляции важнее свежесть кадра, чем обработка каждого кадра.

03.06.2026 - проектирование протокола обмена и разделение ответственности

На этом этапе сравнивались два подхода: отправлять из Python готовые TTL-линии или отправлять сырые координаты точек. Был выбран второй подход: Python выполняет только зрение и упаковку данных, а Open Ephys plugin принимает решение о TTL.

  • Python: камера, DLCLive/PyTorch, raw pose points.
  • C++ plugin: фильтрация, triplet, угол, TTL.
  • Фиксированный набор данных: 6 точек в формате [x, y, likelihood].
  • UDP port: 47000.

Вывод: перенос decision logic в C++ уменьшает нагрузку Python и делает Open Ephys центральным местом управления стимуляцией.

04.06.2026 - проверка C++ bridge и TTL pipeline

Была проверена C++-сторона Open Ephys bridge. Она должна принимать UDP-пакет, разбирать координаты, проверять валидность точек, считать угол и формировать TTL word.

  • Основной формат: binary DDLP/v1.
  • Размер пакета: около 252 bytes.
  • TTL line 0: валиден левый triplet.
  • TTL line 1: валиден правый triplet.
  • TTL line 2: left angle trigger.
  • TTL line 3: right angle trigger.

Вывод: binary pose стал основным рабочим форматом, так как он быстрее и компактнее JSON.

05.06.2026 - safety-анализ и отказоустойчивость

День был посвящен проверке рисков. Рассматривались ситуации остановки Python, потери UDP-пакета, пропажи точек, NaN-заглушки правой стороны и отключенного angle trigger.

  • Порог использования точки: conf_thresh_use = 0.20.
  • Порог видимого triplet: conf_thresh_draw = 0.15.
  • Despike threshold: 150 px.
  • Median window: 3.
  • Angle threshold на старте: около 55 deg.

Вывод: C++ plugin должен строго проверять finite значения, а для финального эксперимента нужен watchdog свежести данных.

06.06.2026 - методика сравнения режимов

Были определены критерии, по которым можно сравнивать разные варианты запуска: скорость, задержка, число видимых точек, стабильность likelihood и поведение TTL.

  • Сравниваемые режимы: FP32+TF32, strict FP32, FP16.
  • Отдельно сравниваются preview и headless.
  • Отдельно проверяется RGB no-convert и BGR to RGB fallback.

Вывод: FPS сам по себе недостаточен. Нужно одновременно смотреть inference time, raw visible points, likelihood и TTL behavior.

07.06.2026 - анализ latency и CPU/GPU нагрузки

На этом этапе проверялась гипотеза, почему видео может выглядеть запаздывающим. Главный вывод: задержка складывается из нескольких стадий, а не только из инференса нейросети.

  • camera/read;
  • preprocess;
  • inference;
  • pack/send;
  • display.

Также было установлено, что низкая видимая загрузка GPU в Task Manager не означает, что модель работает на CPU. PyTorch подтверждал CUDA и устройство cuda:0.

Вывод: CPU остается важным, потому что камера, OpenCV, display, упаковка и Python scheduling не исчезают даже при GPU-инференсе.

08.06.2026 - end-to-end архитектура и цветовой путь

Была разобрана полная цепочка от камеры до TTL и отдельно проверен вопрос RGB/BGR. Это было важно, потому что неправильный порядок каналов может резко ухудшить точность модели.

  • Рабочий вариант: камера отдает RGB.
  • DLCLive conversion отключен.
  • Модель получает RGB без лишнего CPU shuffle.
  • Программный crop не нужен, так как используется аппаратный ROI.
  • Resize: 1.0.
  • Dynamic cropping выключен.

Вывод: цветовой путь в рабочем режиме корректен, а лишняя конвертация убрана ради снижения CPU-нагрузки.

09.06.2026 - основной realtime-прогресс и single-camera режим

Двухкамерный режим был технически подготовлен, но правая камера не давала полезную детекцию. Типичная картина: левая сторона имеет около 3/6 видимых точек, правая сторона часто имеет 0/6, likelihood правой стороны около 0.01. Поэтому был создан практический single-camera режим.

  • Активная камера: левая FDE22070174.
  • Правая сторона пакета: NaN.
  • Правые TTL-линии должны оставаться неактивными.
  • UDP формат остался тем же, чтобы плагин не требовал отдельного single-протокола.

По запросу пользователя preview-видео было включено для всех режимов запуска, чтобы можно было смотреть, как точки ложатся на животное. Для финальной стимуляции сохранен отдельный headless запуск без окна.

7. Выводы Для Не-Программистов

  1. Система уже умеет в реальном времени получать изображение с камеры и находить точки конечности.
  2. Основная рабочая камера сейчас левая. Правая камера требует физической перенастройки.
  3. Скорость достаточна для визуального контроля: около 38-42 FPS после warm-up.
  4. Окно с видео полезно для проверки, но для реальной стимуляции его лучше выключать.
  5. Решение о стимуляции теперь находится в Open Ephys, что логичнее для эксперимента.

8. Выводы Для Программистов

  1. Основной bottleneck - DLCLive/PyTorch inference, обычно 17-21 ms в single-camera режиме.
  2. pack/send не является bottleneck: около 0.12 ms.
  3. Display стоит дорого: около 5 ms, поэтому нужен headless mode.
  4. Binary DDLP/v1 оправдан как основной протокол, JSON оставить как fallback/debug.
  5. FP16 нельзя включать в финальный эксперимент без сравнения TTL behavior с FP32.
  6. Нужен watchdog свежести данных, чтобы stale frame не мог привести к неверной стимуляции.

9. Рекомендации Для Следующего Этапа

  • Перед финальной стимуляцией запускать headless-режим без preview.
  • Физически перенастроить правую камеру и повторить проверку raw visible для правой стороны.
  • Проверить в Open Ephys: растет ли счетчик UDP packets, mode = binary, TTL lines работают ожидаемо.
  • Сравнить FP32+TF32 и strict FP32 на одних и тех же данных около порога угла.
  • Добавить watchdog свежести кадров и явную диагностику потери UDP-пакетов.
  • FP16 оставить только как экспериментальный режим до отдельной валидации координат и TTL.

10. Итог

За период 02.06.2026-10.06.2026 система была доведена до воспроизводимого realtime-прототипа. Было принято архитектурно важное решение: Python отвечает за видеопоток и нейросетевую оценку позы, а Open Ephys plugin отвечает за фильтрацию, расчет угла и формирование TTL. Это делает систему более понятной, быстрее в Python-части и удобнее для дальнейшей настройки стимуляции.

Текущий наиболее надежный режим: single-camera left, FP32+TF32, RGB no-convert, binary pose to Open Ephys, C++ plugin decision logic. Для проверки точек используется preview, для финальной стимуляции рекомендуется headless-режим.
